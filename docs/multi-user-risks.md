# 複数人同時利用時のリスク（handoff-board 側で回収）

> 出自: handoff-mcp の設計中に判明（handoff-mcp ADR-0002「メールは便宜フィルタ・ローカル単一運用者前提」）。
> 当面は **単一運用者 + 各自ローカル MCP** を前提とし問題ないが、複数人が同時に handoff-board を
> 使い出すと以下のリスクが顕在化する。対策はいずれも **handoff-board 側**の変更で行う。

## 前提（このリスクが成立する条件）

- MCP は各自ローカルで stdio 起動（HTTP 公開しない）。MCP 自体の詐称はここでは対象外。
- handoff-board は共有。複数メールのユーザーが Web UI / 各自の MCP から同時にアクセスする。
- `BOARD_TOKENS` は `{token: actor}`。MCP 用トークンは actor=運用者メールにしている。

## 現状の認可モデル（コード上の事実）

- **認証**: `X-Board-Token`（機械系）→ actor=トークンのマップ値 / `Authorization: Bearer`（人間=Firebase）→ actor=検証済みメール。
- **読取** `GET /api/board`:
  - 人間パス → `findAll({createdBy: 当人})` で自分の作成分のみ。
  - 機械系パス → `findAll()` で **全件（絞り込まない）**。
- **書込** `POST`（created_by=actor を付与）/ `PATCH`（status 遷移）/ `PATCH /details`（編集）/ `DELETE` / `POST /complete`:
  - **いずれも created_by の所有チェックをしていない**。認証が通れば id 指定で誰のタスクでも操作可。
- 遷移は ADR-0002 のステートマシンで強制、楽観ロック（updated_at→409）あり。

→ **「自分のタスクだけ」というスコープは、読取は人間パスのみ・書込はどこにも無い**。
MCP の per-user 分離は MCP のクライアント側フィルタ（善意）で成立しているだけ。

## リスク一覧

| # | リスク | 深刻度 | 内容 |
|---|---|---|---|
| R1 | 機械系トークンの read が全件 | 高 | 有効なトークンを1つ持てば、**全ユーザーのタスクを閲覧可能**。MCP のメールフィルタはサーバーで強制されていない（クライアント側のみ）。 |
| R2 | 書込で created_by 非検証 | 高 | 有効なトークン（または別ユーザーの Bearer）で、id を指定すれば **他人のタスクを編集・status 遷移・削除・完了** できる。 |
| R3 | トークン＝メールの全権・ローテーション不在 | 中 | MCP トークンが漏れると、そのメール本人として create でき（created_by 詐称）、上記 R1/R2 と併せて実質全権。トークン失効/ローテーションの手段が無い。 |
| R4 | activity.actor の真正性なし | 中 | 機械系の actor は「トークンに紐づく文字列（メール）」。トークンを持つ者は誰でもそのメールとして記録される。監査ログとして「誰が操作したか」を信頼できない。 |
| R5 | created_by=null のレガシー/機械系作成タスク | 低 | どのユーザーのフィルタにも一致せず、人間ボード・各 MCP から見えない（取り残し）。移行が必要。 |
| R6 | ドメイン許可の広さ | 中 | `ALLOWED_EMAIL_DOMAINS=sunbit.co.jp` によりドメイン内の誰でも人間ログイン可。読取は自分の created_by に絞られるが、**作成は誰でも可能**で、R1/R2（機械系）と併用されると分離が崩れる。 |
| R7 | 共有タスクの並行更新 | 低 | 複数人が同一 created_by を共有運用すると同一タスクの並行編集で 409 が頻発しうる（楽観ロックで安全側だが UX 低下）。 |

## 同時実行時の振る舞い（参考）

- 別人が互いの created_by に触れない通常運用では衝突は起きにくい。
- 同一タスクへの並行更新は **楽観ロック（updated_at 不一致→409 Conflict）** で後勝ちを防止。クライアントは再取得して再試行する。
- 不正遷移は 422、競合は 409 と分離済み（ADR-0002）。これは多人数でもそのまま機能する。

## 推奨対策（handoff-board 側）

優先度順:

1. **C1: 機械系 read をトークン actor で絞る** — `GET /api/board` を機械系でも `findAll({createdBy: actor})` に。
   ただしディスパッチャー（ボード全体から次の作業を拾う）は全件が必要なので、**「ボード全体を見てよいトークン種別」と「個人スコープのトークン」を区別**する設計が要る（例: actor がメール形式なら絞る、種別文字列なら絞らない）。
2. **C2: 書込で所有検証** — PATCH/PATCH details/DELETE/complete で「対象の created_by == 実行 actor」を検証し、不一致は 403。
   （これも C1 同様、ディスパッチャー等のシステム系は例外扱いが必要か要検討。）
3. **C3: トークン管理** — Secret Manager 化、ローテーション手順、漏洩時の失効。トークン=個人メールの紐付けは監査上も脆いので、機械系を「個人代理」に使うこと自体の是非を再検討。
4. **C4: 真の多ユーザーは人間パス中心へ** — 自己申告メール（機械系 actor=メール）をやめ、各ユーザーは Firebase ID トークンで操作。MCP からも人間パスを使う（自己申告をやめる）なら handoff-mcp ADR-0002 の見直しが必要。
5. **C5: created_by=null のバックフィル** — レガシータスクの所有者移行 or 表示ポリシー決定。

## 当面の運用前提（このまま使ってよい条件）

- 運用者が1人、または互いに完全信頼できる少人数のみ。
- MCP は各自ローカル（stdio）で起動し、HTTP/SSE で公開しない。
- MCP トークンを他人と共有しない。
- 上記が崩れる（実質的な多ユーザー化）時点で、最低限 C1・C2 を入れること。
