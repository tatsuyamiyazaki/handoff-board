# 人間承認 Gate の強制をインフラ層（権限・資格情報）に置き、ボードは可視化に純化する（ADR-0005 追補）

## Status

proposed — [ADR-0005](0005-remove-dispatcher-pull-via-mcp.md) の追補（廃止根拠の明確化と Gate 設計の確定）

## 決定

- 人間承認 Gate の粒度は**リスク単位**とする。Gate を要求するのは**社外に影響が出る操作**（本番デプロイ、顧客向けメール送信・成果物提出、公開リポジトリへの push・リリース作成・パッケージ公開）のみ。社内影響に留まる操作（コード作成、社内リポジトリへの push、調査、下書き作成）は承認不要で流す。
- Gate の**可視化はボード**が担う: 社外影響操作は CEO の分解規約（[ADR-0009](0009-ceo-orchestrator-pull-based-sequential-scheduler.md)）により `owner=human` の独立タスクに分離され、既存の `needs-human` ステータスが承認待ちの表現になる。**ボードに新しい状態は追加しない**。ただし CEO 生成タスクが人間のボードに表示されること自体は [ADR-0011](0011-human-board-includes-machine-created-tasks.md)（人間ボードのスコープ拡張）が前提であり、これなしでは本項の可視化は成立しない。
- Gate の**強制はボードの外、インフラ層**が担う。構成は次のとおり:
  1. **第一層（摩擦）**: (a) エージェント実行環境の deny ルール（settings.json）で `gcloud` 等の危険コマンドを拒否する。(b) エージェント専用の GCP サービスアカウント（本番デプロイ権限なし）を作成し、起動スクリプトで `CLOUDSDK_CONFIG` を専用ディレクトリに向けて認証を分離する。**(b) は構造的強制ではない**: エージェントは人間と同一 OS ユーザーで走るため、人間の既定 gcloud 設定・ADC（`%APPDATA%\gcloud` 等）にファイル権限上は到達でき、環境変数の向け直しやサブシェルでの既定構成フォールバックによって**悪意なく**素通りしうる。摩擦としては有効だが、最悪ケースを託す層ではない。
  2. **第二層（構造的強制・デプロイ）**: 本番デプロイを **CI（GitHub Actions）に一本化し、Environment protection rules による人間承認を必須**にする。デプロイ資格情報は CI 環境のみが保持し、**人間のローカルマシンから本番デプロイ資格情報を撤去する**（人間も CI 経由でデプロイする）。これが成立して初めて、どの経路（スクリプト・直接コマンド・MCP）を通っても承認なしのデプロイが物理的に失敗する。**移行完了までの間、デプロイ Gate は第一層＋規約のみであり、これは期限付きの残余リスクとして受容する**。
  3. **第二層（構造的強制・メール）**: エージェントに送信資格情報を渡さない。Google Workspace 系ツールを接続する場合も**許可は `create_draft`（下書き作成）まで**とし、送信は人間が UI で行う。この規約を CLAUDE.md に明文化する。
  4. **第二層（構造的強制・公開系）**: エージェントの git/GitHub 資格情報は**社内（プライベート）リポジトリのみに write を持つ fine-grained PAT** に限定し、npm 等のパッケージ公開トークンは渡さない。社内 push と社外公開（public リポジトリへの push・リリース作成・publish）が**同一資格情報で行える状態を作らない**。ただしこれも、同一 OS ユーザーに人間の git 資格情報（credential manager、`gh auth` 等）が同居する場合は完全ではない（残余リスク参照）。

## 文脈とトレードオフ

ADR-0005 はディスパッチャー廃止を記録したが、その根拠の本質——**AI 実行の前に人間の承認 Gate を挟む**——を明文化していなかった。本追補はこれを明文化した上で、重要な訂正を加える: **pull モデルは Gate を保証しない**。Gate が現に機能しているのは「エージェントは人間がセッションを起動したときしか動かない」という運用実態の産物であり、pull のまま常駐ポーリングを導入すれば Gate は消滅する。Gate を守りたいなら、pull/push の選択に依存させず、明示的な機構に載せなければならない。

その機構をどこに置くか。脅威モデルは「性善説＋事故」——エージェントが悪意で統制を破ることは想定しないが、悪意なく破ることは日常的に起きる——である。この前提で各層を評価すると:

- **規約（CEO の分解ルール、CLAUDE.md）**: LLM 出力に依存し、分解ミスでリスク操作が通常タスクに混入しうる。すり抜けの実害が社内に留まる操作にはこれで足りるが、社外影響には不足。
- **deny ルール**: コマンド文字列のパターンマッチであり、エージェントがコマンド列をスクリプトにまとめて `bash deploy.sh` で実行すれば素通りする。これは敵対的すり抜けではなく Claude Code の標準的な作業パターンであり、**悪意ゼロで Gate を通過する**。第一層の摩擦としては有効だが、最悪ケースを託せる層ではない。
- **MCP ツール層での実行停止**: エージェントはシェルアクセスを持つため、MCP を経由しない実行経路を塞げない。強制にならない。
- **資格情報・IAM**: どの経路（スクリプト・直接コマンド・MCP）を通っても、権限がなければ操作は物理的に失敗する。唯一、事故に対しても強制が成立**しうる**層である。ただし資格情報の分離は、**エージェントが人間の資格情報に到達できない境界（別マシン・別 OS ユーザー・CI 環境）があって初めて成立する**。人間と同一 OS ユーザーで走るローカルエージェントに対しては、環境変数による分離（`CLOUDSDK_CONFIG`）は境界にならない。

したがって、社外影響操作の強制は資格情報・IAM 層に置く——ただし置き方は「ローカルの認証分離」ではなく「**資格情報を人間のマシンごとエージェントの届かない場所（CI 環境）へ移す**」である。起草時は `CLOUDSDK_CONFIG` 分離を構造的強制と位置づけていたが、同一 OS ユーザー問題により摩擦（第一層）へ再分類した。この帰結として、ボードは「承認の実行装置」である必要がなくなり、**承認状態のモデル化と可視化**に責務を純化できる。CI 移行完了後は、すり抜け（CEO の分解ミス等）が起きても権限不足で失敗するため、規約層の不完全さが実害に至らない。

なお顧客向けメールは、現行運用（人間が Gmail UI で送信し、エージェントは送信資格情報を持たない）が既に構造的強制として成立している。決定 3 は新設ではなく、**将来エージェントに Workspace 系ツールを接続した瞬間にこの前提が無言で崩れる**ことへの予防的明文化である。

検討した代替案:

1. **deny ルールのみで強制とする** — 却下（上述。スクリプト経由で悪意なく素通りする）。第一層としては採用。
2. **ローカルの資格情報分離（`CLOUDSDK_CONFIG`＋エージェント専用 SA）を構造的強制とする** — 却下（当初案）。CI 移行という前提工事なしで導入できる利点はあるが、人間と同一 OS ユーザーで走るエージェントには境界として機能しない（上述）。摩擦（第一層）としては採用する。
3. **ボードに `awaiting-approval` 状態を追加し、承認操作を API で表現する** — 却下。強制がインフラ層にある以上、ボード上の承認状態は `needs-human` タスクで表現でき、新状態は冗長。人間が `needs-human` タスクを自ら実行して `done` にする行為が、承認と実行を兼ねる（[ADR-0007](0007-in-review-state-and-review-cycle-limit.md) 導入後は `in-review` 経由となるが、owner=human×人間 actor の自己レビュー例外により単独で通せる）。
4. **タスク属性としてリスクレベルを持たせ、ステートマシンで Gate 遷移を分岐する** — 却下。リスク分類の正しさが CEO（LLM）の申告に依存し、誤分類がそのまま Gate すり抜けになる。強制を申告値に依存させない方針と矛盾する。

## 帰結

- **本 ADR によるボード（api / web / shared）のコード変更はない**。変更対象はエージェント実行環境（settings.json、起動スクリプト、`CLOUDSDK_CONFIG` 分離）、GCP IAM（エージェント専用 SA の作成と最小権限付与）、CLAUDE.md（Gmail draft-only 規約、社外影響操作の定義リスト）、そして**デプロイパイプラインの CI 移行**（GitHub Actions ワークフローの整備、Environment protection rules の設定、ローカルからの本番デプロイ資格情報の撤去、docs/DEPLOYMENT.md の手順更新）である。
- 「社外影響操作」の定義リスト（現時点: 本番デプロイ、顧客向けメール送信、顧客向け成果物の提出、公開リポジトリへの push・リリース作成・パッケージ公開）は CLAUDE.md で管理し、追加時は本 ADR の追補ではなく規約更新で対応する。定義リストと資格情報・IAM 設定の対応は**手動同期**であり、リストへ操作を追加して資格情報側の制限を追加し忘れるとその操作は無防備になる（ドリフト）。リスト更新時は対応する資格情報制限を同一の変更で行うことをチェック項目とする。
- エージェント専用 SA には Firestore・ログ閲覧・ビルド等、作業に必要な最小権限のみ付与する。付与内容は docs/DEPLOYMENT.md に記録する。
- ADR-0005 の決定（pull モデル、ディスパッチャー廃止）は不変。本追補により、将来の無人稼働移行（ADR-0009 の帰結参照）が Gate を破らないことが保証される。
- 残余リスク: 社内影響操作のすり抜け（例: 未検証コードの社内リポジトリ混入）は規約＋レビュー関門（[ADR-0007](0007-in-review-state-and-review-cycle-limit.md)）＋activity による事後追跡（[ADR-0008](0008-agent-identity-role-token-and-session-id.md)）で統制し、構造的強制は行わない。これは意図した受容である。
- 残余リスク: メールの draft-only は「エージェントに送信資格情報を渡さない」ことに依存するが、エージェントが人間と同一 OS ユーザーで走る限り、人間側に同居する資格情報（ブラウザセッション、キャッシュされた OAuth トークン、git credential manager 等）への到達を構造的に塞ぐことはできない。同一 OS ユーザー問題は資格情報分離全般（メール・公開系）に共通する限界であり、完全な境界が必要になったら OS ユーザー分離または実行環境分離（コンテナ/別マシン）を別途決定する。
- 残余リスク（期限付き）: CI 移行完了までの間、本番デプロイの Gate は第一層（deny ルール＋SA/認証分離の摩擦）と規約のみで、構造的強制は存在しない。移行完了までは CEO の分解規約（[ADR-0009](0009-ceo-orchestrator-pull-based-sequential-scheduler.md) 規約 2）のすり抜けが実害に直結しうることを認識して運用する。
