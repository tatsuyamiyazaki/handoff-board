# CEO オーケストレーターを「pull する一エージェント」として導入し、逐次スケジューラ方式で後続タスクを生成する

## Status

proposed

## 決定

- タスク分解・割り当てを担う **CEO エージェント**を導入する。CEO は**サーバー機能ではなく、handoff-mcp 経由でボードを読み書きする一クライアント**である。[ADR-0005](0005-remove-dispatcher-pull-via-mcp.md) の pull モデルは不変。
- CEO の分解規約（エージェント側スキル / CLAUDE.md として管理し、サーバーは関与しない）:
  1. 大タスクを子タスクに分解し、**即座に `needs-ai` で作成**する（承認待ち状態は設けない）。ただし規約 2 で `owner=human` に分離する Gate タスクは **`needs-human` で作成**する——`needs-ai` で作ると承認待ちが承認レーンに現れず、Gate の可視化（[ADR-0010](0010-approval-gate-enforcement-at-infrastructure-layer.md)）が成立しない。サーバーは owner と初期 status の組を強制しない（`validateCreateTask` は初期 status が `needs-ai|needs-human` であることしか検証しない）ため、この対応は分解規約側の責務である。owner / department / role（[ADR-0006](0006-owner-department-role-three-axes.md)）の割り当ても分解時に行う。
  2. **社外に影響が出る操作（本番デプロイ、顧客向け送信・提出等）は、必ず `owner=human` の独立タスクに分離**する。人間承認 Gate はこの分離＋既存の `needs-human` レーンで可視化される（強制は [ADR-0010](0010-approval-gate-enforcement-at-infrastructure-layer.md)）。
  3. 順序依存のある子タスクは、**先行タスクが `done` になった時点で初めて作成**する（逐次スケジューラ）。分解計画の全体は親タスク（下記）の詳細欄・activity に保持し、ボードには「いま実行可能なタスク」しか置かない。
- CEO の作業単位はボード上の**親タスク**（人間が作成する大タスク）である。CEO はこれを通常の pull（`needs-ai → in-progress`）で取得し、オーケストレーション中は `in-progress` に保持し、全子タスク完了後に `in-review` へ進める（レビュー関門は [ADR-0007](0007-in-review-state-and-review-cycle-limit.md) に従う。CEO を特別扱いする状態・スキーマは設けない）。
- 親子リンクのスキーマは追加しない。**子タスクの詳細欄冒頭に親タスク ID を記載する規約**で対応する。複数の大タスクを並行分解しても、`done` になった子タスクがどの計画に属するかはこの記載で判別する。CEO セッションが失われた場合、新しいセッションは親タスクの詳細欄（計画の single source）と子タスクの親 ID 記載から状態を復元する。
- CEO の稼働は**人間の監視下の同期セッション内ループ**とする。人間がセッションを起動している間、CEO は定期的にボードを pull し、`done` を検知して後続を生成する。無人時間帯の自動稼働（タスクスケジューラによる headless 起動）は行わない。

## 文脈とトレードオフ

cc-agent-harness で実証済みの CEO オーケストレーション（タスク分解・ディスパッチ・並列ワーカー管理）を handoff に取り込むにあたり、最大の論点は ADR-0005 で廃止した push 型ディスパッチとの整合だった。ADR-0005 の廃止根拠を掘ると、本質は pull/push の技術選択ではなく「**AI 実行の前に人間の承認 Gate を挟む**」という統制要請である。ただし pull モデル自体は Gate を保証しない——Gate が機能しているのは「エージェントは人間がセッションを起動したときしか動かない」という運用実態によってであり、常駐ポーリングを導入すれば pull のまま Gate は消滅する。したがって Gate は pull/push の選択にではなく、明示的な設計（本 ADR の規約 2 と ADR-0010 の強制）に載せる。

Gate の粒度は**リスク単位**とした。タスク単位の個別承認は人間がボトルネックになり、計画単位の一括承認は不可逆操作の混入を防げない。社外影響（不可逆・深刻）だけを人間タスクに分離し、社内影響に留まる作業（コード作成、社内リポジトリへの push、調査）は承認なしで流す。

分解結果を即 `needs-ai` に流す（`proposed` 承認状態を設けない）のは、リスク操作が規約 2 で `needs-human` に分離される保証がある以上、分解結果の事前レビューは統制上必須でなく、事後にボードと activity で観察すれば足りるため。これによりステートマシンは本件では無変更で済む（`in-review` は別件 [ADR-0007](0007-in-review-state-and-review-cycle-limit.md)）。

逐次スケジューラ（案 II）を依存関係スキーマ（案 I: `depends_on`）より優先したのは、ボードの利用目的が「いま人間がやるべきもの・いま動いているものを見る」ことに確定しているため。未着手の後続まで含む計画全体の可視化ニーズがない以上、循環検出・失敗伝播を伴う依存スキーマは過剰投資である。「状態やスキーマを増やすのではなく、タスクの生成タイミングと分離で表現する」という原理の適用でもある。

同期稼働に限定したのは、無人時間帯の進捗ニーズの実感が運用上存在しないため（cc-agent-harness 運用で「翌朝までに進んでいてほしかった」経験がない）。無人稼働は監視・トークン消費上限・マシン常時稼働という運用コストを伴い、ニーズなき投資となる。なお ADR-0010 により Gate 強制はインフラ層にあるため、将来無人稼働に移行しても Gate は破られない。移行はセッション起動方法の変更のみで可能であり、本決定は拡張パスを塞がない。

検討した代替案:

1. **サーバー側ディスパッチャーの復活（push 型）** — 却下。ADR-0005 の却下理由（push する先のランタイムが存在しない）は今も有効。CEO が必要とするのは「分解と生成」であり、push 実行基盤ではない。
2. **`proposed`（計画承認待ち）状態の追加** — 却下（上述）。承認処理量を増やす割に、リスク統制上の追加保証がない。
3. **`depends_on` による依存関係スキーマ** — 却下（上述）。将来「計画全体をボードで見たい」ニーズが生じたら再検討する。その場合も逐次スケジューラとの併存（CEO が depends_on 付きで一括生成に切り替える）が可能で、本決定は後戻り可能。
4. **無人時間帯の自動稼働** — 却下（上述）。

## 帰結

- **本 ADR によるサーバー・スキーマ変更はない**。ボード（api / web / shared）は CEO を特別扱いしない。CEO は一機械系クライアント（actor 例: `claude-code:ceo`、[ADR-0008](0008-agent-identity-role-token-and-session-id.md)）である。
- CEO の単一障害点性（CEO が止まると後続が生成されない）は、同期稼働の限定により実害が消える。人間がセッションを見ている＝停止に気づける。
- 分解規約・ロール割り当てロジック・逐次スケジューラのループは CEO 側リポジトリ（cc-agent-harness 系スキル）の管理物であり、handoff-board の docs にはインターフェース（本 ADR）のみ残す。
- 規約 2 は CEO の LLM 出力に依存する（分解ミスでリスク操作が通常タスクに混入しうる）。これを許容できるのは、混入しても実行時にインフラ層強制（ADR-0010）で物理的に失敗するためである。**本 ADR 単独で Gate を構成しない**ことに注意。なおデプロイの構造的強制は ADR-0010 の CI 移行完了後に成立する——移行前に CEO 運用を開始する場合、デプロイ Gate は摩擦＋規約のみである（ADR-0010 の期限付き残余リスク参照）。
- stale 掃引を持たない現設計（ADR-0005）は不変。CEO のループが放置タスクに気づいた場合の扱い（人間へ通知するか否か）は CEO 規約側の関心事とする。
- **導入順序の制約**: 「先行タスクが `done` になった時点で後続を作成」は、`done`＝レビュー通過という意味論（ADR-0007）を前提とする。ADR-0007 の導入前に CEO 運用を開始すると、未レビュー成果物を根拠に後続タスクを生成してしまう。また CEO 生成タスク（created_by が機械系）が人間のボードに表示されるためには [ADR-0011](0011-human-board-includes-machine-created-tasks.md) のスコープ拡張が前提であり、これも CEO 運用開始前に必要（未導入のままでは「人間の監視下」と Gate タスクの可視化が成立しない）。
- `done` タスクの archive 掃引（`/complete`）はポーリング間隔の谷間で `done` を不可視にしうる（CEO が完了を検知する前にボードから消える）。CEO 稼働中は archive 操作を行わないか、CEO が archive も照会する — 具体的な取り扱いは CEO 規約側の関心事とする。
- 親タスク詳細欄への計画同期は CEO の規律（LLM 出力）に依存し、スキーマによる保証はない。これは意図した受容であり、復旧不能な破綻が観測されたら `depends_on`（代替案 3）再検討の契機とする。
